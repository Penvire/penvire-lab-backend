# Fine-grained authorization with OpenFGA

Services need relationship-based authorization across tenants, engagements, evidence, custom apps, API tokens and platform administration. Role claims inside JWTs cannot express resource-level relationships and remain stale until token expiry, while separate per-service SQL role tables and authorization caches duplicate logic and drift across services. The lab therefore adopts **OpenFGA** as its shared fine-grained authorization engine and source of truth for authorization relationships, accessed by every service through a shared library (`libs/fga`) that wraps `dev.openfga:openfga-sdk`. The lab mirrors the method intended for the product.

## Decision

- **OpenFGA is the source of truth for authorization relationships.** Permissions, roles and resource-access relationships live in OpenFGA rather than being mirrored in service SQL tables. Services write and delete tuples directly and synchronously through `libs/fga`, giving immediate read-your-own-writes and immediate revocation well within the 5-second revocation target ([`docs/jwt-security-handout.md`](../jwt-security-handout.md#caches-and-outages), lines 121–122).
- **One shared store and one contract-owned authorization model.** All services share a single OpenFGA store and a single modular authorization model maintained in `penvire-lab-contracts` and published as a versioned package ([ADR 0001](0001-versioned-contracts-through-published-packages.md)), where each service owns its module. Because `libs/fga` falls back to the store's latest model when `authorizationModelId` is not pinned, model changes must be expand-and-contract: add new types or relations first, upgrade services, and remove deprecated ones only in a breaking release once no running service queries them.
- **Subjects use the JWT `sub` directly, separated by principal type, under a single trusted issuer.** Human users appear in OpenFGA as `user:<sub>` and autonomous clients or services (`client_credentials`) as `client:<client_id>`. Audit ([ADR 0006](0006-audit-events-recorded-by-each-service.md)) and Identity already key on `sub`, and `libs/security` (`CachingJwksKeyResolver`) accepts only one trusted issuer. Trusting a second issuer is out of scope and requires revisiting this ADR.
- **Each service enforces its own authorization, token restrictions and tuple ownership.** Services never trust edge headers; each checks the required relation in OpenFGA and maintains structural tuples linking its entities to parent objects (for example `engagement:<id>#tenant -> tenant:<id>`). Identity uses OpenFGA for its management operations (such as platform-admin account actions, and later custom apps, API tokens and consent), not for core OIDC protocol flows, invite redemption, self-service password changes or break-glass signing-key revocation. When a custom app or API token acts on behalf of a user, OpenFGA still evaluates `user:<sub>` and does not enforce custom-app tenant confinement or API-token tenant and scope restrictions ([`GLOSSARY.md`](../../GLOSSARY.md)); per [`docs/jwt-security-handout.md`](../jwt-security-handout.md#principals-and-tenant-authorization), each API separately enforces token validity, scopes and tenant binding from the verified JWT alongside the OpenFGA check.
- **Dual-write ordering fails toward less access.** Because a service database transaction and an OpenFGA write are two separate operations without distributed transactions:
  - Changes that **remove** access (revocations, role downgrades, resource deletes) write to OpenFGA **before** committing the database transaction. If the OpenFGA delete fails, the database transaction rolls back and leaves no `SUCCESS` audit event; if the database commit fails after OpenFGA removed the tuple, access is already revoked (fail-closed).
  - Changes that **add** access (new grants, role promotions, initial ownership on create) write to OpenFGA **after** the database transaction commits. If the database transaction rolls back, no OpenFGA grant is ever written. If the post-commit OpenFGA write fails, the committed state and its `SUCCESS` audit event (with [ADR 0008](0008-audited-actions-choose-recorded-failures.md)'s default `failedOn = {}`) lack the new grant until retried, while logs and traces capture the failure; partial failure never leaves unintended access.
- **Fail closed on outages and integrate with HTTP problem details and auditing.** If OpenFGA is unreachable, times out, rate-limits (HTTP 429) or returns a 5xx server error, `libs/fga` throws `FgaUnavailableException`, which `libs/fga` maps to `503 Service Unavailable` (`application/problem+json`) via `libs/problem` without leaking internal details. Client-side 4xx errors throw plain `FgaException` (HTTP 500) as programming or model errors. Checks default to `HIGHER_CONSISTENCY` so revocations take effect immediately. Authorization refusals via `require(...)` throw Quarkus `ForbiddenException`, which `@Audited` actions record as `DENIED` automatically ([ADR 0008](0008-audited-actions-choose-recorded-failures.md)).
- **One shared library `libs/fga` wraps `dev.openfga:openfga-sdk`.** Services never depend on SDK request/response types or `CompletableFuture` APIs directly. `libs/fga` exposes a small, synchronous, `@NullMarked` CDI facade (`FgaClient`) with validated value types (`FgaSubject`, `FgaObject`, `FgaTuple`) that block tuple-string injection and wildcards.
- **SQLite backs local OpenFGA in `devenv`.** Because local `devenv` does not run a shared PostgreSQL server (services rely on Quarkus Dev Services for their own databases), local OpenFGA runs on SQLite under `$DEVENV_STATE/openfga` and exports traces to the local OpenTelemetry Collector.
- **What this replaces in [`docs/jwt-security-handout.md`](../jwt-security-handout.md):** the `Principals and tenant authorization` bullets mapping `(iss, sub)` to separate Tenant-owned `principalId` UUIDs (lines 105–112) and the `Caches and outages` bullet specifying per-service Tenant authorization caches (line 122).

## Considered options

- **Tenant-owned SQL role tables with per-service authorization caches** (sketched earlier in `docs/jwt-security-handout.md`). Rejected: every service would have to build resource-level authorization rules and bounded invalidation caches, and cross-resource hierarchies do not fit flat tenant roles.
- **Separate application `principalId` mapped from `(iss, sub)` in Tenant.** Rejected: every request to every service would pay a lookup and cache hop before calling OpenFGA, Identity would gain a circular dependency on Tenant, and Audit (`sub`) and authorization (`principalId`) would split user identity across two IDs.
- **Syncing OpenFGA tuples asynchronously through the transactional outbox and Kafka.** Rejected: consumer lag or failures delay revocation past the 5-second target and break read-your-own-writes immediately after creating a resource.
- **Using `dev.openfga:openfga-sdk` directly in each service, or a third-party Quarkus extension.** Rejected: calling the raw SDK repeats `CompletableFuture` handling, stringly-typed `type:id` formatting, error translation and idempotency options in every service; third-party Quarkus extensions lag Quarkus upgrades and reduce control over the SDK.

## Consequences

- Protected requests fail closed with `503 Service Unavailable` whenever OpenFGA is unavailable, timed out or rate-limited; OpenFGA is therefore critical infrastructure that must be monitored through OpenTelemetry.
- Per-service tuple ownership is a convention, not enforced by OpenFGA: any service with credentials to the shared store can write or delete any tuple in that store (for example Engagement could technically write a `tenant:<id>#admin` tuple).
- Because dual writes are not atomic across PostgreSQL and OpenFGA, post-commit grant failures require retry or reconciliation; partial failures always err toward less access, never more.
- Adopting a second trusted token issuer, or migrating to an external identity provider that cannot preserve existing `sub` UUIDs, requires revisiting this ADR (either via a custom token claim or a tuple migration).
- Services remain free to add short-lived caching later only if measured latency requires it and revocation freshness stays within 5 seconds.
